# Code Review（代码审查）

<what-to-do>

读代码，找问题，给建议。不要凭感觉评判，要读实际代码、跑测试、查上下文后再下结论。

**行为规则：**

1. **先读代码再说话。** 不要看到文件名就下结论。打开文件，读实现，理解逻辑链，再评判。

2. **先验证后评判。** 能跑测试就跑测试，能编译就编译。不要说"这里可能有问题"——要么确认有问题，要么确认没问题。

3. **分级输出。** 问题分三级：Critical（必须修）、Important（应该修）、Minor（锦上添花）。不要把所有问题都标成 Critical。

4. **先说做得好的。** 在指出问题之前，先肯定做得好的地方。准确的肯定能让开发者信任后面的反馈。

5. **每个问题说清楚三件事：** 在哪（文件:行号）、为什么有问题、怎么修。

6. **有 PRD 或架构决策就对照审查。** 实现是否符合需求？是否遵循了当初的架构决策？偏离了是改进还是遗漏？

</what-to-do>

<supporting-info>

## 使用方式

### 手动触发

```
/code-review                                  # 审查当前未提交的变更
/code-review src/main/java/UserService.java   # 审查指定文件
/code-review @docs/prd/user.md                # 对照 PRD 审查
/code-review --staged                         # 审查已暂存的变更
```

### 自动触发

其他 skill 在以下时机应自动执行 code-review，不需要用户手动调用：

| 触发时机 | 触发者 | 审查范围 |
|---------|--------|---------|
| 写完一个完整功能后 | design | 刚生成/修改的代码文件 |
| TDD 全部绿灯后 | tdd | 实现代码（重构前基线检查） |
| 合并前 | 用户或 frontend-flow | 本次变更的全部文件 |

自动触发时，审查者应派一个**独立子 agent** 执行，不共享调用者的对话历史。这样可以避免"理解了思路就觉得代码没问题"的偏差。

**子 agent 派发方式：**

```
1. 收集变更文件列表（git diff 或调用者提供）
2. 读取相关 PRD / 架构决策（如有）
3. 派发子 agent，传入：
   - 变更文件列表
   - 相关 PRD / 架构决策内容
   - 审查 prompt（见下方"审查者 Prompt"）
4. 子 agent 返回审查报告
5. 汇总报告展示给用户
```

## 审查前准备

```
1. 确定审查范围：
   - 用户指定了文件 → 读这些文件
   - 用户指定了 PRD → 读 PRD，定位相关代码文件
   - 无参数 → git diff 查看未提交变更；无变更则审查最近一次提交

2. 探测项目信息：
   - 语言和框架（看构建文件和依赖）
   - 项目结构和分层
   - 已有的 lint / format 配置
   - 已有的测试覆盖

3. 读取相关上下文（如有）：
   - docs/prd/ — 需求文档（probe-me 生成的 PRD 文件头包含 `source: probe-me` 标识，优先消费有此标识的文件）
   - docs/adr/ 或 PRD 中的"架构决策"章节
   - docs/api/ — 接口文档
```

## 检查维度

按优先级从高到低检查：

### 1. 正确性（最容易出 Critical）

- 逻辑错误：条件判断反了、边界条件漏了、空值没处理
- 并发问题：竞态条件、死锁、线程不安全
- 数据问题：数据丢失、精度丢失、编码问题

### 2. 安全性

- SQL 注入、XSS、命令注入
- 敏感信息硬编码（密码、密钥、token）
- 权限校验缺失
- 输入未校验就使用

### 3. PRD / 架构决策对齐（如有）

- PRD 要求的功能是否都实现了
- 架构决策是否被遵循（偏离了是改进还是遗漏）
- 接口定义是否和接口文档一致

### 4. 错误处理

- 异常是否被捕获和处理
- 错误信息是否有意义
- 资源是否正确释放（连接、流、锁）

### 5. 可维护性

- 命名是否清晰
- 函数是否过长
- 重复代码是否该提取
- 职责是否清晰

### 6. 性能

- N+1 查询
- 大数据量未分页
- 不必要的全表扫描
- 内存泄漏风险

### 7. 测试

- 新代码是否有测试
- 测试是否覆盖了关键路径
- 测试是否测的是行为而非实现

## 分级标准

| 级别 | 含义 | 处理要求 |
|------|------|---------|
| Critical | 会出 bug、安全漏洞、数据丢失 | 必须立即修复 |
| Important | 架构问题、功能遗漏、错误处理缺失 | 应在合并前修复 |
| Minor | 命名、格式、优化机会、文档补全 | 可以后续处理 |

## 输出格式

```
## 审查范围

- 文件：{审查的文件列表}
- 关联文档：{PRD / 接口文档 / 架构决策，如有}
- 变更类型：{新增功能 / Bug 修复 / 重构}

## 做得好的

- {具体的优点，引用文件:行号}

## 问题

### Critical

#### 1. {问题简述}
- **位置**：`file:line`
- **问题**：{具体描述}
- **影响**：{会导致什么后果}
- **建议**：{怎么修}

### Important

#### 1. {问题简述}
- **位置**：`file:line`
- **问题**：{具体描述}
- **建议**：{怎么修}

### Minor

1. `{file:line}` — {问题简述}，建议 {怎么修}

## 总结

**可合并？** {可以 | 修复后可合并 | 不建议合并}

**理由：** {1-2 句技术评估}
```

## 审查原则

### 不要做的事

- 不要凭名字下结论，要读实现
- 不要说"可能有问题"，要么确认要么排除
- 不要把风格偏好标成 Critical
- 不要给没有上下文的模糊建议（"优化一下"）
- 不要一次性提出超过 10 个问题（优先级不够会淹没真正重要的）

### 要做的事

- 能跑测试就跑，用结果说话
- 对照 PRD 逐条检查功能完整性
- 对照架构决策检查是否遵循
- 发现好的设计实践要明确肯定
- 不确定的地方标注"需确认"，不要当问题提

### 被反驳时

如果开发者对你的反馈提出质疑：
- 用技术理由回应，不要坚持"我是 reviewer 所以我说了算"
- 如果对方说得对，承认并更新结论
- 如果无法确定，建议一起验证

## 审查者 Prompt（子 agent 使用）

自动触发时，用以下 prompt 派发独立子 agent：

```
你是一位高级代码审查员。你的工作是审查已完成的代码变更，对照需求和架构决策，找出问题。

## 审查范围

{变更文件列表，或 git diff 范围}

## 需求 / 架构决策

{PRD 内容摘要，或"无"}

## 你需要检查的

**需求对齐：**
- 实现是否符合 PRD / 需求？
- 偏离是改进还是遗漏？
- 所有计划的功能都实现了吗？

**代码质量：**
- 关注点是否分离？
- 错误处理是否完善？
- 类型安全（如适用）？
- DRY 但不过早抽象？
- 边界情况是否处理？

**架构：**
- 设计决策是否合理？
- 性能和可扩展性？
- 安全问题？
- 是否和现有代码风格一致？

**测试：**
- 测试是否测的是真实行为？
- 边界情况是否覆盖？
- 所有测试是否通过？

## 校准

按实际严重程度分级。不是所有问题都 Critical。
先肯定做得好的地方，再列问题。
发现和计划的重大偏离要明确标出。

## 输出格式

### 做得好的
[具体优点，引用 file:line]

### 问题

#### Critical（必须修）
[bug、安全问题、数据丢失风险]

#### Important（应该修）
[架构问题、功能遗漏、错误处理缺失]

#### Minor（锦上添花）
[风格、优化、文档]

每个问题：file:line + 问题描述 + 影响 + 修复建议

### 总结

**可合并？** [可以 | 修复后可合并 | 不建议合并]
**理由：** [1-2 句技术评估]
```

</reviewer-prompt>
