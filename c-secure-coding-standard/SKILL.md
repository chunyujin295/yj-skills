# C&C++ 语言安全编程规范

本规范旨在加强编程人员的安全意识，建立攻击者思维，养成安全编码的习惯，编写出安全可靠的代码。

## 安全编码基本思想

### 攻击者思维

编程过程中应时刻保持以下假设：
1. 程序所处理的所有**外部数据都是不可信的攻击数据**
2. 攻击者时刻试图**监听、篡改、破坏**程序运行环境、外部数据

### 三大原则

1. **程序在处理外部数据时必须经过严格的合法性校验** — 不能做出任何外部数据符合预期的假设。
2. **尽量减少代码的攻击面** — 代码实现应尽量简单，避免与外部环境做多余的数据交互。
3. **通过防御性的编码策略来弥补潜在的编码人员疏忽** — 变量声明赋予初值、谨慎使用全局变量、禁用易用错的函数、严格错误处理、合理使用 ASSERT。

### 外部数据定义

以下均视为外部（不可信）数据：文件（含配置文件）、注册表、网络、环境变量、命令行、用户输入、用户态数据（内核程序）、进程间通信（管道/消息/共享内存/socket/RPC）、函数参数（对 API 而言）、全局变量（其他线程可能修改）。

## 1. 基础要求

### 1.1 变量

#### 规则

- **规则 1.1.1**：指针变量、表示资源描述符的变量、`BOOL` 变量**声明时必须赋予初值**。例如：`SOCKET s = INVALID_SOCKET;`、`char *message = NULL;`、`BOOL success = FALSE;`、`int fd = -1;`。例外：全局变量、静态变量在编译阶段自动初始化为 0/NULL，不需要强制初始化。

- **规则 1.1.2**：指向资源句柄或描述符的变量，在资源释放后**立即赋予新值**。防止悬挂指针（double-free 或 use-after-free）。如果释放语句刚好在变量作用域最后一句，可以不赋值。

- **规则 1.1.3 （C++）**：类的成员变量必须在构造函数中赋予初值。

- **规则 1.1.4**：**严禁对指针变量进行 `sizeof` 操作**。`sizeof(ptr)` 返回的是指针大小而非指针所指内容大小。正确的做法是 `sizeof(*ptr)` 或 `sizeof(type)`。

#### 建议

- **建议 1.1.1**：尽量使用 `const`，利用编译器进行类型检查，将代码权限降到最低。
- **建议 1.1.2**：全局变量访问如果涉及多个线程，必须加锁。性能敏感时考虑原子操作或无锁算法。
- **建议 1.1.3**：同一个函数内，局部变量所占空间不要过大。静态数组建议不超过 `0x1000`（4096 字节），避免 stack overflow。

### 1.2 断言（ASSERT）

#### 规则

- **规则 1.2.1**：断言必须使用宏定义，**禁止直接调用** `assert()`。断言在发布版中必须通过编译选项控制为无效。
  ```c
  #ifdef DEBUG
  #define ASSERT(f) assert(f)
  #else
  #define ASSERT(f) ((void)0)
  #endif
  ```

- **规则 1.2.2**：**运行时可能会导致的错误，严禁使用断言**。断言只能用于验证代码设计上的假设（如"上层调用者保证了参数不可能为 NULL"），不能用于校验文件打开、内存分配、外部输入等运行时可能发生的错误。

- **规则 1.2.3**：**严禁在断言内改变运行环境**（赋值、修改变量、资源操作、内存申请等）。

#### 建议

- **建议 1.2.1**：不要将多条语句放在同一个断言中，每条断言只校验一个条件，以便准确定位错误。

### 1.3 函数

#### 规则

- **规则 1.3.1**：**数组作为函数参数时，必须同时将其长度作为函数的参数**。防止越界访问。例外：`const char *` 类型（以 `'\0'` 判断结尾）、以特定元素值判断结尾的 `const struct *` 数组、性能敏感且长度可保证的固定长度数组。

- **规则 1.3.2**：**严禁对公共接口 API 函数的参数进行 ASSERT 操作**。API 函数必须对参数进行代码级别的合法性判断，不能在 API 实现中产生 CRASH。

- **规则 1.3.3**：不对内容进行修改的指针型参数，定义为 `const`。

#### 建议

- **建议 1.3.1**：谨慎使用不可重入函数（如 `rand`、`strtok`、`getenv`、`asctime`、`localtime`、`gethostbyname`、`inet_ntoa` 等）。
- **建议 1.3.2**：字符串或指针作为函数参数时，必须检查参数是否为 `NULL`。
- **建议 1.3.3**：在函数的开始处对参数进行 ASSERT 操作（API 除外）。

### 1.4 循环

- **规则 1.4.1**：循环必须有退出条件。例外：操作系统 IDLE 线程、不可恢复错误中的无限循环、嵌入式设备主流程。

### 1.5 异常机制（C++）

- **规则 1.5.1**：**禁用 C++ 异常机制**。所有错误通过返回值在函数之间传递。例外：接管 C++ 语言自身抛出的异常（如 `new` 失败）、第三方库抛出的异常。

### 1.6 类（C++）

- **规则 1.6.1**：如果有构造函数，则必须有析构函数。
- **规则 1.6.2**：构造函数内不能做任何有可能失败的操作（如 `open`、`new`、`ConnectServer`）。
- **规则 1.6.3**：严禁在构造函数中创建线程。
- **规则 1.6.4**：严禁出现 `delete this` 操作。谁申请，谁释放。
- **规则 1.6.5**：如果类的公共接口中返回类的私有数据地址，则必须加 `const` 类型。

### 1.7 安全退出

- **规则 1.7.1**：禁用 `atexit` 函数。资源不再使用时应立即主动清理，不应被动等待。
- **规则 1.7.2**：严禁调用 `kill`、`TerminateProcess` 函数终止其他进程。应先通知对方安全退出，超时后方可强制终止。
- **规则 1.7.3**：禁用 `pthread_exit`、`ExitThread` 函数。线程函数执行完毕后自动安全退出。
- **建议 1.7.1**：禁用 `exit`、`ExitProcess` 函数（`main` 函数除外）。程序应通过错误值传递机制进行错误处理。
- **建议 1.7.2**：禁用 `abort` 函数（致命错误处理函数中除外）。

## 2. 字符串 / 数组操作

- **规则 2.1**：确保有足够的存储空间。注意 `itoa`、`realpath` 等函数对缓冲区大小的隐含要求。
- **规则 2.2**：对字符串进行存储操作，确保字符串有 `'\0'` 结束符，否则后续 `strlen` 等操作会内存越界。
- **规则 2.3**：外部数据作为数组索引时必须确保在数组大小范围内。
- **规则 2.4**：外部输入作为内存操作函数（`memcpy`、`memmove`、`memcpy_s`、`memmove_s`）的复制长度时，必须校验其合法性。
- **规则 2.5**：调用格式化函数时，**禁止 format 参数由外部可控**。这些函数包括：`xxxprintf`、`xxxscanf`、`err()`/`warn()` 系列、`syslog()`。
- **规则 2.6**：调用格式化函数时，format 中参数的类型与个数必须与实际参数类型一致。例外：`signed char`/`signed short` 可用 `%d`，`unsigned char`/`unsigned short` 可用 `%u`。

## 3. 正确使用安全函数

- **规则 3.1**：正确设置安全函数中的 `destMax` 参数，应准确、有效。
- **规则 3.2**：**禁止不正确地重定义或封装安全函数**。不得忽略 `destMax` 参数或将其与 `count` 混用；不得用宏重命名危险函数为安全函数名。
- **规则 3.3**：禁止用宏重命名安全函数。这不利于静态代码扫描工具的规则定制。
- **规则 3.4**：禁止自定义安全函数。使用标准 C11 安全函数（如 `memcpy_s`、`strcpy_s`、`strcat_s` 等）。
- **规则 3.5**：必须检查安全函数返回值，并进行正确的处理。如果返回值 `!= EOK`，本函数应立即返回。例外：安全函数返回值检查的错误处理代码中调用安全函数可以不检查；规则 6.6 例外场景中可不检查。

## 4. 整数

- **规则 4.1**：整数之间运算时必须严格检查，确保不会出现**溢出、反转、除 0**。
- **规则 4.2**：整型表达式比较或赋值为一种更大类型之前必须用这种更大类型对它进行求值（先转型再运算）。
- **规则 4.3**：**禁止对有符号整数进行位操作符运算**（`~`、`>>`、`<<`、`&`、`^`、`|`）。
- **规则 4.4**：**禁止整数与指针间的互相转化**。使用 `uintptr_t` 类型替代。
- **规则 4.5**：**禁止对指针进行逻辑或位运算**（`&&`、`||`、`!`、`~`、`>>`、`<<`、`&`、`^`、`|`）。检查指针应使用 `!= NULL` 或 `== NULL`。例外：检查地址对齐的位运算。
- **规则 4.6**：循环次数如果受外部数据控制，需要校验其合法性（防止死循环或越界）。

## 5. 内存

- **规则 5.1**：内存申请前，必须对申请内存大小进行合法性校验。不能申请 0 长度的内存。
- **规则 5.2**：内存分配后必须判断是否成功（`malloc` 返回 `NULL` 检查）。
- **规则 5.3**：**禁止引用未初始化的内存**。`malloc` 分配的内存未被初始化为 0，使用前须用 `memset_s` 初始化。
- **规则 5.4**：内存释放之后**立即赋予新值**（指针置 `NULL`），消除悬挂指针。
- **规则 5.5**：**禁止使用 `realloc()` 函数**。此函数行为多变（分配/重新分配/释放），极易引发 bug。
- **规则 5.6**：禁止使用 `alloca()` 函数申请栈上内存。使用 `malloc` 或 `new` 从堆中分配。

## 6. 不安全函数

- **规则 6.1**：**禁止外部可控数据作为进程启动函数的参数**。这些函数包括：`system`、`popen`、`WinExec`、`ShellExecute`、`execl`/`execlp`/`execle`/`execv`/`execvp`、`CreateProcess`。如需使用，必须用**白名单机制**校验参数。建议 Linux/Unix 下使用 `exec` 系列函数（但禁止使用 `/bin/sh`），Windows 下使用 `CreateProcess`（注意空格和参数解析器问题）。

- **规则 6.2**：**禁止外部可控数据作为模块加载函数的参数**。函数包括：`dlopen`、`LoadLibrary`。例外：有密钥/签名保护的动态模块。

- **规则 6.3**：**禁止使用外部数据拼接 SQL 命令**。必须使用：参数化查询（预处理语句）优先、ODBC 参数化查询、不可信数据白名单校验、SQL 特殊字符转义。

- **规则 6.4**：**禁止在信号处理例程中调用非异步安全函数**。信号处理例程应尽可能简化。

- **规则 6.5**：**禁用 `setjmp`/`longjmp`**。它们使程序复杂难懂，资源不能有效清理，且无法在多线程环境下使用。

- **规则 6.6**：**禁止使用内存操作类危险函数**，使用对应的安全函数替代：

| 危险函数 | 替换为安全函数 |
|----------|--------------|
| `memcpy`/`wmemcpy` | `memcpy_s`/`wmemcpy_s` |
| `memmove`/`wmemmove` | `memmove_s`/`wmemmove_s` |
| `memset` | `memset_s` |
| `strcpy`/`wcscpy` | `strcpy_s`/`wcscpy_s` |
| `strncpy`/`wcsncpy` | `strncpy_s`/`wcsncpy_s` |
| `strcat`/`wcscat` | `strcat_s`/`wcscat_s` |
| `strncat`/`wcsncat` | `strncat_s`/`wcsncat_s` |
| `sprintf`/`swprintf` | `sprintf_s`/`swprintf_s` |
| `vsprintf`/`vswprintf` | `vsprintf_s`/`vswprintf_s` |
| `scanf`/`wscanf` 系列 | `scanf_s`/`wscanf_s` 系列 |
| `gets` | `gets_s` |

**例外**：以下场景可以留用危险函数（不涉及外部数据、无被攻击场景）：
- （1）对固定长度数组初始化
- （2）对函数参数中传入的内存初始化
- （3）从堆中分配内存后赋初值
- （4）基于 `srcSize` 分配等大内存后复制
- （5）源内存全部是静态字符串常量
- （6）Visual Studio 2005+ 开发 Windows 程序时已使用微软安全函数

## 7. 文件输入 / 输出

- **规则 7.1**：创建文件时必须显式指定合适的文件访问权限。如：`open(fileName, O_CREAT | O_WRONLY, S_IRUSR | S_IWUSR);`
- **规则 7.2**：必须对文件路径进行规范化后再使用。Linux 下使用 `realpath()`，Windows 下使用 `PathCanonicalize()`，然后校验路径是否合法。
- **规则 7.3**：不要在共享目录中创建临时文件。
- **建议 7.1**：在进行文件操作时避免引起竞争条件（TOCTOU — Time-of-check Time-of-use）。

## 8. 敏感信息处理

- **规则 8.1**：**禁用 `rand` 函数产生用于安全用途的伪随机数**。使用 `/dev/random` 或密码学安全的随机数生成器。
- **规则 8.2**：**内存中的敏感信息（口令、密钥）使用完毕后立即清 0**。使用 `memset_s()` 而非 `memset()`（编译器可能优化掉 `memset()`）。Windows 下可用 `SecureZeroMemory()`，或使用 `#pragma optimize("", off)` 防止优化。
- **规则 8.3**：**严禁使用 `string` 类存储敏感信息**（C++）。`string` 可能在内存中产生多份副本，无法安全清 0。应使用 `char[]` 或 `unsigned char[]` 存储并在使用后清 0。

## 附录：快速检查清单

审查 C/C++ 代码安全性时，逐项检查：

1. ☐ 指针/资源变量是否声明即初始化？
2. ☐ 资源释放后指针是否立即置 NULL/new 值？
3. ☐ 数组作为参数时是否同时传递了长度？
4. ☐ 外部数据使用前是否经过严格的合法性校验？
5. ☐ 断言是否正确使用（宏定义、不改变环境、不用于运行时错误）？
6. ☐ 格式化函数的 format 参数是否外部不可控？
7. ☐ 整数运算是否检查溢出/反转/除 0？
8. ☐ 是否使用安全函数替代了危险字符串/内存操作函数？
9. ☐ 安全函数的 destMax 参数是否正确？返回值是否检查？
10. ☐ 内存申请前是否校验大小？分配后是否检查成功？使用前是否已初始化？
11. ☐ 是否禁止了 `realloc`、`alloca`、`setjmp`/`longjmp`？
12. ☐ system/popen/exec 系列参数是否外部不可控？
13. ☐ SQL 语句是否使用参数化查询？
14. ☐ 文件路径是否规范化？文件权限是否显式设置？
15. ☐ 敏感信息使用后是否安全清 0（用 `memset_s`）？
16. ☐ C++ 中是否禁用了异常机制和 string 存储敏感信息？
17. ☐ 循环是否有退出条件？外部控制的循环次数是否校验？
18. ☐ 是否正确处理了 C++ 类的构造/析构/成员权限？
