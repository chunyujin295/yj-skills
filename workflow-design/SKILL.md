# Workflow 阶段 2：深度设计（Design）

通过结构化 brainstorming 将想法变成完整的技术设计。

## 前置条件

- 活跃 change 已存在（proposal.md、tasks.md 已创建）

## 脚本定位

```bash
WF_SCRIPT="${WF_SCRIPT:-$(find . "$HOME"/.*/skills "$HOME/.config" "$HOME/.trae" \
  -path '*/workflow/scripts/wf.sh' -type f -print -quit 2>/dev/null)}"
if [ -z "$WF_SCRIPT" ]; then
  echo "ERROR: wf.sh not found. Ensure the workflow skill is installed." >&2
  exit 1
fi
```

---

## HARD-GATE

**在你展示设计并获得用户批准之前，不得编写任何代码、搭建任何项目或采取任何实施行动。** 这适用于每一个变更，无论其看起来多么简单。

### 反模式："这太简单了，不需要设计"

每个变更都经过这个流程。一个配置变更、一个单函数工具——全部都是。"简单"的变更是未被审视的假设导致最多返工的地方。设计可以很短（真正简单的项目几句话），但你**必须**展示它并获得批准。

---

## Step 0: 入口状态验证

```bash
"$WF_SCRIPT" state check <name> design
```

验证通过后继续。验证失败时报告具体原因。

**幂等性**：design 阶段所有操作可安全重复执行。

---

## Step 1: 项目上下文探索

**立即执行：** 探索当前项目上下文。

- 读取 `workflow/changes/<name>/proposal.md`（理解需求和范围）
- 扫描代码库：
  - 文件结构和目录布局
  - 现有架构模式
  - 技术栈和依赖
  - 测试基础设施
- 读取 recent commits（`git log --oneline -10`，了解团队风格和最近变更）
- 如有 docs/ 目录，扫描相关文档

### 在已有代码库中工作

- 提出变更前先探索当前结构。遵循现有模式。
- 如果现有代码有问题影响当前工作（如文件过大、职责不清），在设计中包含有针对性的改进。
- 不提议无关的重构。专注于服务当前目标。

---

## Step 2: 结构化提问

探索完成后，**逐个提问**以细化需求。

### 提问原则

- **一次一个问题** — 不要用多个问题淹没用户
- **优先选择题** — 比开放式更容易回答
- **选择题格式**：
  ```
  A. <选项 1> — <简要说明>
  B. <选项 2> — <简要说明>
  C. <选项 3> — <简要说明>
  推荐 A，因为 <理由>
  ```

### 关注维度

- **目的**：这个变更要解决什么问题？
- **约束**：技术约束、性能约束、兼容性约束、时间约束
- **成功标准**：怎么知道做完了？怎么验证？

### 范围评估

如果 proposal 描述了多个独立子系统，**立即标记**。不要花时间细化一个需要先拆分的项目。帮用户拆分：独立的部分有哪些、它们的关系、应该按什么顺序构建？然后把第一个子项目走完正常设计流程。

---

## Step 3: 提出 2-3 个方案

理解需求后，提出 2-3 个不同的实现方案。

### 方案格式

每个方案包含：
- **思路**：怎么做
- **优点**：为什么好
- **缺点**：什么代价
- **推荐理由**：为什么推荐（或不推荐）

### 展示方式

用对比表格呈现：

```
                方案 A          方案 B          方案 C
思路            <简述>          <简述>          <简述>
优点            <列出>          <列出>          <列出>
缺点            <列出>          <列出>          <列出>
复杂度          低              中              高
推荐            ✅              ⚠️              ❌
```

**带推荐选项**，解释为什么。引领推荐选项并解释原因。

---

## Step 4: 分段展示设计

用户选择方案后，分段展示完整设计。

### 展示原则

- **按复杂度缩放**：简单的几句话，复杂的 200-300 字
- **每段确认后再继续**
- 覆盖：架构、组件、数据流、错误处理、测试策略

### 设计原则

- **隔离性和清晰性**：把系统拆成更小的单元，每个单元有一个清晰的目的，通过定义良好的接口通信，可以独立理解和测试
- **对每个单元**：能回答它做什么、怎么用、依赖什么
- **有人能不读内部就理解一个单元做什么吗？** 能在不破坏消费者的情况下修改内部吗？如果不能，边界需要改进
- **更小、边界清晰的单元**也更容易处理——你能更好地推理一次能放进上下文的代码

### 每段确认

展示每段后问："这部分看起来对吗？" 用户指出问题时，回到澄清或修改设计。

---

## Step 5: 用户确认设计方案（阻塞点）

设计展示完成后，**必须使用 AskUserQuestion 暂停并等待用户明确确认设计方案**。不得在用户确认前写入 design.md 或进入 `/workflow-build`。

暂停时展示：
- 采用的技术方案
- 关键取舍与风险
- 测试策略

**选项**：
- 「确认，写入 design.md」
- 「需要调整」— 附带调整说明

用户确认后才继续。若用户要求调整，继续迭代，直到用户确认。

---

## Step 6: 写入 design.md

将确认的设计方案写入 `workflow/changes/<name>/design.md`。

### design.md 结构

```markdown
# <Change Name> — 技术设计

## 架构决策

<!-- 选了什么方案、为什么、放弃了什么 -->

## 技术方案

<!-- 详细的实现方案，包括组件拆分、数据流、接口定义 -->

## 关键取舍

<!-- 做了哪些权衡，为什么 -->

## 风险评估

<!-- 可能出什么问题，如何缓解 -->

## 测试策略

<!-- 怎么验证，测什么 -->
```

---

## Step 7: Spec 自检

写入 design.md 后，用全新的眼光审视：

1. **占位符扫描**：有 "TBD"、"TODO"、不完整章节或模糊需求吗？修复它们。
2. **内部一致性**：各章节是否矛盾？架构是否匹配功能描述？
3. **范围检查**：是否聚焦到单个实施计划，还是需要拆分？
4. **歧义检查**：有需求可以有两种解读吗？如果有，选一个并明确写出来。

发现问题直接内联修复。不需要重新审查——修复后继续。

---

## Step 8: 用户审阅（阻塞点）

Spec 自检通过后，**请用户审阅 design.md 文件**：

> "design.md 已写入 `workflow/changes/<name>/design.md`。请审阅，如有修改意见请告知，确认后我们进入计划与构建阶段。"

等待用户回复。如用户请求修改，修改后重新执行 Step 7 自检。用户确认后才继续。

---

## Step 9: 更新状态

```bash
"$WF_SCRIPT" state set <name> design_doc workflow/changes/<name>/design.md
"$WF_SCRIPT" guard <name> design --apply
```
