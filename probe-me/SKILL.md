# Probe-me（需求 + 方案对齐）

<what-to-do>

先把需求问清楚，再把方案对齐，最终产出一份结构化 PRD 文档。

**行为规则：**

1. **先探索，再提问。** 用户说"给用户管理加功能"，先读 `src/views/user/` 的代码，识别现有字段、组件结构、API 调用方式，再针对性追问。不要问代码里已经有的信息。

2. **一次问一个关键问题。** 涉及功能决策（"需要导出吗？""编辑是弹窗还是跳转？"）的问题逐个问，等用户反馈再继续。简单的确认类问题（"分页默认 10 条？"）可以合并 2-3 个一起问。

3. **实时写入 PRD。** 每确认一个决策点，立刻写入 PRD 对应章节，不要等全部确认完再一起写。对话过程中 PRD 是"在建工程"，用户随时能看到已确认的内容。

4. **交叉验证。** 用户说的需求和代码现状矛盾时，直接指出来。比如用户说"列表支持分页"，但代码里用的是静态数组，要指出来一起对齐。

5. **方案对齐融入追问过程。** 不是先问完需求再问方案，而是在需求确认过程中自然地问技术方案。比如确认完"要导出"就接着问"前端生成还是后端生成"。

6. **标注决策理由。** 涉及技术选型的决策（数据获取策略、导出方式等），不只记录"选了什么"，还要记录"为什么选"和"放弃了什么"。简单 UI 偏好（"弹窗还是跳转"）不需要记录理由。

</what-to-do>

<supporting-info>

## 使用方式

```
/probe-me 我想做一个用户管理页面           # 自然语言描述
/probe-me @docs/backend-prd.md           # 读取后端 PRD，转为前端 PRD
/probe-me 给用户管理增加导出功能           # 修改现有功能
```

## 路径解析

- `{skill_path}` = 本 skill 所在目录的绝对路径
- `{project_path}` = 用户当前工作目录

## 文档路径约定

| 文档类型 | 路径 | 说明 |
|---------|------|------|
| 前端 PRD | `docs/prd/` | 本 skill 输出 |
| 接口文档 | `docs/api/` | api-doc skill 输出 |
| 设计原型 | `docs/design-prototype/` | design skill 输出 |

写入前自动创建目录：`mkdir -p`。

## 代码探索策略

在提问之前，先从代码获取信息：

1. **现有页面**：读 `src/views/{模块名}/index.vue`，识别字段、表格列、搜索条件、操作按钮、组件拆分方式
2. **API 封装**：读同目录的 `api.js` / `api.ts`，识别已有接口函数
3. **Mock 数据**：读 `mock.js` / `mock.ts`，识别 mock 数据结构
4. **路由配置**：读 `src/router/` 确认页面路径

能从代码读到的信息不要问用户。只问代码里没有的、需要用户决策的问题。

## 追问维度

根据需求复杂度自动选择追问数量：
- 简单 CRUD（< 5 字段）→ 问 3-5 个关键问题
- 中等复杂度（5-15 字段）→ 问 5-8 个
- 高复杂度（> 15 字段或含图表/流程）→ 问 8-12 个

**功能维度**（逐个问）：

| 维度 | 问题示例 |
|------|---------|
| 字段定义 | "列表需要哪些字段？字段类型是什么？" |
| 搜索条件 | "需要搜索功能吗？搜索哪些字段？" |
| 操作功能 | "需要新增/编辑/删除吗？" |
| 交互方式 | "编辑是弹窗还是跳转新页面？" |
| 状态管理 | "状态字段有哪些值？" |
| 分页配置 | "每页多少条？默认10条？" |
| 导出功能 | "需要导出吗？导出格式是什么？" |
| 权限控制 | "需要权限控制吗？" |

**技术方案维度**（融入追问过程）：

| 维度 | 问题示例 | 何时问 |
|------|---------|--------|
| 数据获取策略 | "后端分页还是一次加载？" | 确认列表功能后 |
| 表单校验 | "需要前端校验吗？校验规则？" | 确认表单字段后 |
| 文件处理 | "导出前端生成还是后端生成？" | 确认导出功能后 |
| 树形/级联 | "数据有层级关系吗？" | 确认列表结构后 |
| 批量操作 | "需要批量删除或批量修改吗？" | 确认操作功能后 |
| 状态同步 | "编辑后自动刷新列表？" | 确认编辑功能后 |

## 与 design skill 的衔接

```
/probe-me → 输出 docs/prd/{模块名}-{时间戳}.md
                ↓
/design @docs/prd/{模块名}-{时间戳}.md → 读取 PRD → 生成代码
                ↓
后端项目执行 /api-doc → 生成 docs/api/{模块名}-{时间戳}.md
                ↓
复制接口文档到前端项目 docs/api/ 后：
/design @docs/prd/{模块名}-{时间戳}.md @docs/api/{模块名}-{时间戳}.md → 对接真实接口
```

## 接口能力需求

> 前端需要的接口能力，不代表真实后端路径。真实接口以 api-doc 扫描后端代码生成的 docs/api/*.md 为准。

| 能力 | 接口状态 | 前端入参 | 前端期望响应 | 说明 |
|------|---------|---------|-------------|------|
| 获取列表 | 待扫描 | 页码、每页条数、keyword | 列表数据、总数 | 用于表格分页查询 |

**接口状态**：待扫描 / 用户提供 / 已确认真实接口

## 架构决策

> 用户确认的技术决策，供 design / tdd / code-review 参考。每条记录"选了什么 + 为什么 + 放弃了什么"。无重要决策时可省略本章。

| 决策点 | 选择 | 理由 | 放弃的方案 |
|--------|------|------|-----------|
| 数据获取 | 后端分页 | 数据量可能超过 1 万条 | 前端一次加载 |
| 导出方式 | 前端生成 Excel | 不依赖后端接口 | 后端生成下载链接 |
