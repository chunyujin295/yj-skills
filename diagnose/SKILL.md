# Diagnose（问题诊断）

<what-to-do>

找到根因再修。不猜、不试、不凑。

**铁律：没有完成根因调查，不允许提修复方案。**

看到"可能"、"试试"、"先改这个看看"——停，回到根因调查。

**行为规则：**

1. **先建反馈循环。** 有可靠的 pass/fail 信号，后面一切都是机械操作。没有信号，盯着代码看多久都没用。

2. **一次只改一个变量。** 同时改多个东西，你不知道哪个起了作用。

3. **3 次修不好就质疑架构。** 如果每次修完都冒出新问题，不是你修得不够多，是架构有问题。停下来讨论。

4. **先修再写测试，还是先写测试再修？** 先写失败的测试（如果能找到正确的测试入口）。测试证明修复有效，并防止回归。

5. **修完必须清理。** DEBUG 日志、临时脚本、试验性代码——全部删掉。

</what-to-do>

## 使用方式

```
/diagnose 用户列表查询偶尔返回空                        # 非确定性 bug
/diagnose 提交表单后页面白屏                            # 功能 bug
/diagnose 接口响应从 200ms 变成 2s                      # 性能回归
/diagnose CI 上测试全挂但本地正常                       # 环境问题
```

## 适用场景

任何技术问题都可以用：
- 测试失败
- 生产 bug
- 意外行为
- 性能问题
- 构建失败
- 集成问题

**尤其在这些情况下要用：**
- 时间紧（紧急情况最容易乱猜）
- "一个小修复就好"看似显而易见
- 已经试了好几个修复都没用
- 上次修没修好
- 不完全理解问题

## 阶段 1：建反馈循环（最关键）

**这是整个技能的核心。** 有了快速、确定性的 pass/fail 信号，找到根因只是时间问题。

花不成比例的精力在这里。激进一点，创造性一点，不放弃。

### 建循环的方法（按优先级）

1. **写失败测试** — 在合适的测试入口（单元 / 集成 / 端到端）写一个能复现 bug 的测试
2. **HTTP 脚本** — curl / 脚本对运行中的 dev server 发请求
3. **CLI 命令** — 给定输入，diff 输出和已知正确的快照
4. **无头浏览器** — Playwright / Puppeteer，驱动 UI，断言 DOM / console / network
5. **回放捕获的 trace** — 把真实请求 / payload / 事件日志存到磁盘，在隔离环境回放
6. **临时 harness** — 最小化子系统（一个 service + mock 依赖），用单个函数调用触发 bug 路径
7. **属性 / fuzz 循环** — 如果 bug 是"输出有时不对"，跑 1000 个随机输入找失败模式
8. **二分 harness** — bug 出现在两个已知状态之间，自动化"在状态 X 启动、检查、重复"，配合 `git bisect run`
9. **差分循环** — 同一输入分别跑旧版和新版（或两种配置），diff 输出
10. **手动循环（最后手段）** — 如果必须人工操作，用结构化的脚本驱动，记录输出

### 优化循环本身

把循环当产品来打磨：

- **能更快吗？** 缓存初始化、跳过无关步骤、缩小测试范围
- **信号更明确吗？** 断言具体症状，不是"没崩溃"
- **更确定性吗？** 固定时间、固定随机种子、隔离文件系统、冻结网络

30 秒的不稳定循环 ≈ 没有循环。2 秒的确定性循环 = 调试超能力。

### 非确定性 bug

目标不是完美复现，而是**提高复现率**。

循环触发 100 次、并行化、加压力、缩小时间窗口、注入 sleep。50% 复现率的 bug 可以调，1% 的不行——先把复现率拉上来。

### 真的建不出循环？

停下来，明确说出来。列出你试过什么。问用户要：
- 访问能复现的环境
- 捕获的产物（HAR 文件、日志、core dump、带时间戳的录屏）
- 允许加临时生产环境插桩

**不要在没有循环的情况下进入下一阶段。**

## 阶段 2：复现

运行循环，看到 bug 出现。

确认：
- [ ] 循环产生的就是**用户描述的那个 bug**，不是旁边另一个问题
- [ ] 多次运行都能复现（非确定性 bug 至少高频率复现）
- [ ] 捕获了准确的症状（错误信息、错误输出、慢的耗时）

不能复现就不进入下一阶段。

</workflow>

<workflow>

## 阶段 3：假设

在测试任何假设之前，先列出 **3-5 个排序的假设**。单假设容易锚定在第一个看起来合理的解释上。

每个假设必须**可证伪**：说出它做出的预测。

> 格式："如果 <X> 是根因，那么 <改变 Y> 会让 bug 消失 / <改变 Z> 会让 bug 更严重。"

说不出预测的假设 = 感觉，扔掉或细化。

**展示给用户再测试。** 用户往往有领域知识能立刻重排序（"我们刚部署了第三个假设涉及的改动"）。如果用户不在，按自己的排序继续。

</workflow>

<workflow>

## 阶段 4：插桩

每个探测必须对应阶段 3 的一个具体预测。**一次只改一个变量。**

工具偏好：
1. **调试器 / REPL** — 如果环境支持，一个断点抵十个日志
2. **定向日志** — 只在区分假设的边界点加日志
3. **不要"全打日志然后 grep"**

**给每个调试日志打标签**，如 `[DEBUG-a4f2]`。清理时一条 grep 全删。没标签的调试日志会遗留。

### 性能分支

性能回归不要靠日志，靠**测量**：建立基线（计时 harness、profiler、查询计划），然后二分。先量后修。

</workflow>

<workflow>

## 阶段 5：修复 + 回归测试

**在修之前写回归测试**——但前提是有一个**正确的测试入口**。

正确的测试入口 = 测试能在调用层面真实复现 bug 模式。如果唯一可用的入口太浅（单调用者测试但 bug 需要多调用者链路），回归测试会给假信心。

**如果没有正确的测试入口，记录下来。** 代码架构阻止了 bug 被锁定。

有正确入口时：
1. 把最小化复现变成失败测试
2. 看到它失败
3. 修
4. 看到它通过
5. 重新跑阶段 1 的循环（原始场景，非最小化）

</workflow>

<workflow>

## 阶段 6：清理 + 复盘

完成前必须：

- [ ] 原始复现不再复现（重跑阶段 1 循环）
- [ ] 回归测试通过（或缺少测试入口已记录）
- [ ] 所有 `[DEBUG-...]` 插桩已删除（grep 确认）
- [ ] 临时脚本和原型已删除
- [ ] commit message 里写明哪个假设是正确的——让下一个人学到东西

**最后问：什么能防止这个 bug？** 如果答案涉及架构改动（没有好的测试入口、调用链纠缠、隐式耦合），记下来，修完 bug 后再处理。先修后改架构，因为你现在信息更多。

</workflow>

## 根因回溯法

bug 往往出现在调用栈深处。本能反应是在出错的地方修，但那是在治症状。

**原则：沿调用链往回追溯，找到最初的触发点，在源头修。**

```
观察症状 → 找到直接原因 → 谁调用了这里？ → 继续往上 → 找到源头 → 在源头修
```

### 回溯过程

1. **观察症状**：错误信息是什么？在哪一行？
2. **找直接原因**：哪行代码直接导致的？
3. **谁调用了这里？** 往上一层看
4. **传进来的值是什么？** 空值？错误类型？
5. **继续往上**直到找到值的源头
6. **在源头修**，不只是在症状处修

### 修完后加逐层防御

找到根因后，在数据经过的每一层都加校验：

| 层级 | 防御措施 |
|------|---------|
| 入口层 | 参数校验（空值、类型、范围） |
| 业务层 | 业务规则校验 |
| 环境层 | 环境变量、配置检查 |
| 调试层 | 关键操作前的日志记录 |

不要只在一层修。多层防御互相补充，每层都可能拦住其他层漏掉的路径。

</techniques>

## 3 次修不好 → 质疑架构

| 已尝试修复次数 | 动作 |
|---|---|
| < 3 | 回到阶段 1，用新信息重新分析 |
| ≥ 3 | 停下来，质疑架构 |

**架构有问题的信号：**
- 每次修完都冒出新问题
- 修复需要"大规模重构"
- 每个修处在不同地方暴露新的共享状态 / 耦合

**这不是假设失败，是架构失败。** 和用户讨论是否要重构架构，而不是继续打补丁。

</techniques>

## 常见反模式

| 反模式 | 真相 |
|--------|------|
| "先试这个修修看" | 第一次修复定了基调。从根因开始。 |
| "紧急，没时间走流程" | 系统化调试比乱猜快。 |
| "修完再补测试" | 没测试的修复站不住。先测试。 |
| "同时改多个省时间" | 分不清哪个起了作用，引入新 bug。 |
| "问题简单不需要流程" | 简单问题也有根因。流程对简单 bug 也快。 |
| "看到问题了，直接修" | 看到症状 ≠ 理解根因。 |
| "再试一次"（已试 2 次以上） | 3 次失败 = 架构问题。质疑模式，不要再修。 |

</techniques>

## 非确定性 bug 专项

偶现 bug 是最难的。策略不是追求完美复现，而是**把复现率拉到可以调试的程度**。

| 复现率 | 策略 |
|--------|------|
| > 50% | 直接循环跑，足够调试 |
| 10-50% | 加压力（并发、大数据量、慢速机器） |
| 1-10% | 二分：找引入 bug 的 commit / 配置 / 数据 |
| < 1% | 要求生产环境日志或监控数据，人工排查 |

**关键技巧：**
- 循环触发 100 次统计复现率
- 并行化增加冲突概率
- 注入 sleep 放大时间窗口
- 固定随机种子消除随机因素
- 冻结时间消除时间依赖

</techniques>

## 条件等待（替代任意 sleep）

测试中的 `sleep(500)` 是 flaky 的根源。用条件等待替代：

```
❌ sleep(500)  // 猜的
✅ 等到 result != null  // 等的是真正关心的条件
```

等事件、等状态、等数量、等文件——等的是条件，不是时间。

唯一的例外：当你在测的就是**时间行为**（节流、防抖），可以 sleep，但要注释为什么。

</techniques>

| 阶段 | 关键动作 | 通过标准 |
|------|---------|---------|
| 1. 建循环 | 找到可靠的 pass/fail 信号 | 能一键复现 bug |
