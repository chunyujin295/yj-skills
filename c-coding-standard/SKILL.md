# C 语言编程规范

适用范围：公司内使用 C 语言编码的所有软件。本规范是编写 C 语言程序的基本原则、规则和建议。

## 核心原则

1. **清晰第一** — 代码首先是给人读的，好的代码应可以像文章一样发声朗诵出来。可阅读性高于性能，只有确定性能是瓶颈时才应主动优化。
2. **简洁为美** — 代码越长越难懂、越容易出错。废弃代码要及时清除，重复代码应提炼成函数。
3. **选择合适的风格，与代码原有风格保持一致** — 修改/重构其他风格的代码时，根据现有风格继续编写，或使用格式转换工具统一。

## 术语定义

- **原则**：编程时必须坚持的指导思想
- **规则**：编程时强制必须遵守的约定
- **建议**：编程时必须加以考虑的约定

## 1. 头文件

### 原则

- **原则 1.1**：头文件中适合放置接口的声明，不适合放置实现。内部函数声明、宏、枚举、结构定义不应放入头文件。变量定义不应放在头文件中。
- **原则 1.2**：头文件应当职责单一。头文件过于复杂是编译时间过长的主要原因。
- **原则 1.3**：头文件应向稳定的方向包含。产品依赖于平台，平台依赖于标准库。

### 规则

- **规则 1.1**：每一个 `.c` 文件应有一个同名 `.h` 文件，用于声明对外公开的接口。例外：程序入口（如 main 函数所在的文件）和特别简单的头文件（如命令 ID 定义）。
- **规则 1.2**：禁止头文件循环依赖。
- **规则 1.3**：`.c/.h` 文件禁止包含用不到的头文件。
- **规则 1.4**：头文件应当自包含。任意一个头文件均可独立编译。
- **规则 1.5**：总是编写内部 `#include` 保护符。命名格式：`PROJECTNAME_PATH_FILENAME_H`。不要以 `_` 开头。
- **规则 1.6**：禁止在头文件中定义变量。
- **规则 1.7**：只能通过包含头文件的方式使用其他 `.c` 提供的接口，禁止在 `.c` 中通过 `extern` 方式使用外部函数接口、变量。
- **规则 1.8**：禁止在 `extern "C"` 中包含头文件。

### 建议

- **建议 1.1**：一个模块包含多个 `.c` 文件，建议放在同一目录下，目录名即为模块名。建议每一个模块提供一个 `.h`，文件名为目录名。
- **建议 1.3**：头文件不要使用非习惯用法的扩展名（如 `.inc`）。
- **建议 1.4**：同一产品统一包含头文件排列方式（功能块排序、文件名升序、或稳定度排序）。

## 2. 函数

### 原则

- **原则 2.1**：一个函数仅完成一件功能。避免像 `realloc` 那样的多职责设计。
- **原则 2.2**：重复代码应该尽可能提炼成函数。当代码重复两次时应考虑消除，超过三次时应立即着手消除。

### 规则

- **规则 2.1**：避免函数过长，新增函数不超过 **50 行**（非空非注释行）。例外：实现算法的函数可能超过 50 行。
- **规则 2.2**：避免函数的代码块嵌套过深，新增函数的代码块嵌套不超过 **4 层**。
- **规则 2.3**：可重入函数应避免使用共享变量（全局变量和 `static` 变量）；若需要使用，则必须通过互斥手段（关中断、信号量）对其加以保护。
- **规则 2.4**：对参数的合法性检查，由调用者负责还是由接口函数负责，应在项目组/模块内统一规定。**缺省由调用者负责**。
- **规则 2.5**：对函数的错误返回码要全面处理。调用函数后应在返回时立刻检查错误指示。
- **规则 2.6**：设计高扇入，合理扇出（小于 7）的函数。扇出过大缺乏中间层次，扇出过小调用层次可能过多。
- **规则 2.7**：废弃代码（没有被调用的函数和变量）要及时清除。

### 建议

- **建议 2.1**：函数不变参数使用 `const`。
- **建议 2.2**：函数应避免使用全局变量、静态局部变量和 I/O 操作，不可避免的地方应集中使用。
- **建议 2.3**：检查函数所有非参数输入的有效性（数据文件、公共变量等）。
- **建议 2.4**：函数的参数个数不超过 **5 个**。
- **建议 2.5**：除打印类函数外，不要使用可变长参函数。
- **建议 2.6**：在源文件范围内声明和定义的所有函数，除非外部可见，否则应该增加 `static` 关键字。

## 3. 标识符命名与定义

### 原则

- **原则 3.1**：标识符的命名要清晰、明了，有明确含义，使用完整的单词或大家基本可以理解的缩写。
- **原则 3.2**：除了常见的通用缩写以外，不使用单词缩写，不得使用汉语拼音。

### 规则

- **规则 3.1**：产品/项目组内部应保持统一的命名风格（Unix-like 或 Windows-like，不推荐匈牙利命名法）。
- **规则 3.2**：全局变量应增加 `g_` 前缀。
- **规则 3.3**：静态变量应增加 `s_` 前缀。
- **规则 3.4**：禁止使用单字节命名变量，但允许定义 `i`、`j`、`k` 作为局部循环变量。
- **规则 3.5**：对于数值或字符串常量的定义，采用**全大写字母**，单词之间加下划线 `_` 的方式命名（枚举同样适用）。
- **规则 3.6**：除了头文件或编译开关等特殊标识定义，宏定义不能使用下划线 `_` 开头和结尾。

### 建议

- **建议 3.1**：用正确的反义词组命名具有互斥意义的变量（如 `add/remove`、`create/destroy`、`lock/unlock`）。
- **建议 3.2**：尽量避免名字中出现数字编号。
- **建议 3.3**：标识符前不应添加模块、项目、产品、部门的名称作为前缀。
- **建议 3.6**：文件命名统一采用小写字符。
- **建议 3.7**：不建议使用匈牙利命名法。
- **建议 3.9**：函数命名应以函数要执行的动作命名，采用动词或动词+名词的结构。

## 4. 变量

### 原则

- **原则 4.1**：一个变量只有一个功能，不能把一个变量用作多种用途。
- **原则 4.2**：结构功能单一；不要设计面面俱到的数据结构。
- **原则 4.3**：不用或者少用全局变量。单个文件内部可使用 `static` 的全局变量。

### 规则

- **规则 4.1**：防止局部变量与全局变量同名。
- **规则 4.2**：通讯过程中使用的结构，必须注意字节序（主机序 ↔ 网络序转换）。
- **规则 4.3**：严禁使用未经初始化的变量作为右值。

### 建议

- **建议 4.1**：构造仅有一个模块或函数可以修改、创建，而其余模块只访问的全局变量。
- **建议 4.2**：使用面向接口编程思想，通过 API 访问数据，同时注意全局数据的访问互斥。
- **建议 4.3**：在首次使用前初始化变量，初始化的地方离使用的地方越近越好。
- **建议 4.4**：明确全局变量的初始化顺序，避免跨模块的初始化依赖。
- **建议 4.5**：尽量减少没有必要的数据类型默认转换与强制转换。

## 5. 宏、常量

### 规则

- **规则 5.1**：用宏定义表达式时，要使用完备的括号。正确定义：`#define RECTANGLE_AREA(a, b) ((a) * (b))`
- **规则 5.2**：将宏所定义的多条表达式放在大括号中。更好的方法是使用 `do { ... } while(0)` 方式。
- **规则 5.3**：使用宏时，不允许参数发生变化（如 `SQUARE(a++)` 会导致 a 被加两次）。
- **规则 5.4**：不允许直接使用魔鬼数字。必须定义 `const` 全局变量/宏。

### 建议

- **建议 5.1**：除非必要，应尽可能使用函数代替宏。
- **建议 5.2**：常量建议使用 `const` 定义代替宏。
- **建议 5.3**：宏定义中尽量不使用 `return`、`goto`、`continue`、`break` 等改变程序流程的语句。

## 6. 质量保证

### 原则

- **原则 6.1**：代码质量保证优先原则（优先级从高到低）：正确性 → 简洁性 → 可维护性 → 可靠性 → 可测试性 → 性能高效 → 可移植性 → 个人表达方式。
- **原则 6.2**：要时刻注意易混淆的操作符（`=` vs `==`、`<` vs `<<`、`||` vs `|`、`&&` vs `&`、`!` vs `~`）。
- **原则 6.3**：必须了解编译系统的内存分配方式。
- **原则 6.4**：不仅关注接口，同样要关注实现。

### 规则

- **规则 6.1**：禁止内存操作越界。使用安全函数替代危险函数（`sprintf`→`snprintf`、`strcpy`→`strncpy`、`strcat`→`strncat`、`gets`→`fgets`）；字符串考虑最后的 `'\0'`；数组下标进行检查；使用 `sizeof` 或 `strlen` 而非手工计算。
- **规则 6.2**：禁止内存泄漏。异常出口处检查所有资源是否释放；释放结构指针时必须从底层向上层顺序删除；检查队列中每个成员是否释放。
- **规则 6.3**：禁止引用已经释放的内存空间。内存释放后把指针置为 `NULL`；使用内存指针前进行非空判断。
- **规则 6.4**：编程时，要防止差 1 错误（`<=` vs `<`、`>=` vs `>`）。
- **规则 6.5**：所有的 `if ... else if` 结构应该由 `else` 子句结束；`switch` 语句必须有 `default` 分支。

### 建议

- **建议 6.1**：函数中分配的内存，在函数退出之前要释放。在申请处加上注释，说明在何处释放。
- **建议 6.2**：`if` 语句尽量加上 `else` 分支。
- **建议 6.3**：不要滥用 `goto` 语句。`goto` 可用于统一错误处理出口，使代码更清晰。
- **建议 6.4**：时刻注意表达式是否会上溢、下溢。

## 7. 程序效率

### 原则

- **原则 7.1**：在保证软件系统的正确性、简洁、可维护性、可靠性及可测性的前提下，提高代码效率。**让一个正确的程序更快速，比让一个足够快的程序正确，要容易得太多。**
- **原则 7.2**：通过对数据结构、程序算法的优化来提高效率。

### 建议

- **建议 7.1**：将不变条件的计算移到循环体外。
- **建议 7.2**：对于多维大数组，避免来回跳跃式访问数组成员（注意 cache 局部性）。
- **建议 7.3**：创建资源库（线程池、内存池），以减少分配对象的开销。
- **建议 7.4**：将多次被调用的小函数改为 `inline` 函数或宏实现。

## 8. 注释

### 原则

- **原则 8.1**：优秀的代码可以自我解释，不通过注释即可轻易读懂。注释无法把糟糕的代码变好。
- **原则 8.2**：注释的内容要清楚、明了，含义准确，防止注释二义性。
- **原则 8.3**：在代码的功能、意图层次上进行注释，说明**为什么（why）**，而不是重复描述代码**做了什么（what）**。

### 规则

- **规则 8.1**：修改代码时，维护代码周边的所有注释，保证注释与代码的一致性。不再有用的注释要删除。
- **规则 8.2**：文件头部应进行注释，必须列出：版权说明、版本号、生成日期、作者、功能说明、修改日志等。版权声明格式：`Copyright © [公司名] Technologies Co., Ltd. [年份]. All rights reserved.`
- **规则 8.3**：函数声明处注释描述函数功能、性能及用法（输入输出参数、返回值、可重入要求等）；定义处详细描述实现要点。
- **规则 8.4**：全局变量要有较详细的注释（功能、取值范围、存取注意事项）。
- **规则 8.5**：注释应放在其代码上方相邻位置或右方，不可放在下面。
- **规则 8.6**：`switch` 的 `case` 语句如果需要 fall-through，必须在中间加上明确注释。
- **规则 8.7**：避免在注释中使用缩写，除非是业界通用或子系统内标准化的缩写。
- **规则 8.8**：同一产品或项目组统一注释风格。

### 建议

- **建议 8.1**：避免在一行代码或表达式的中间插入注释。
- **建议 8.2**：注释语言建议多使用中文（有外籍员工时由产品确定）。
- **建议 8.3**：文件头、函数头、全局常量变量、类型定义的注释格式采用工具可识别的格式（如 doxygen）。

## 9. 排版与格式

### 规则

- **规则 9.1**：程序块采用缩进风格编写，每级缩进为 **4 个空格**。
- **规则 9.2**：相对独立的程序块之间、变量说明之后必须加空行。
- **规则 9.3**：一条语句不能过长，如需要换行，应在低优先级操作符处换行，操作符放在新行首，换行后增加一级缩进。
- **规则 9.4**：多个短语句不允许写在同一行内，即**一行只写一条语句**。
- **规则 9.5**：`if`、`for`、`do`、`while`、`case`、`switch`、`default` 等语句独占一行。
- **规则 9.6**：双目操作符前后加空格，单目操作符（`!`、`~`、`++`、`--`、`&`地址操作）前后不加空格，`->`、`.` 前后不加空格，`if`/`for`/`while`/`switch` 等与后面的括号间应加空格。

### 建议

- **建议 9.1**：注释符（`/*`、`//`、`*/`）与注释内容之间要用一个空格分隔。
- **建议 9.2**：源程序中关系较为紧密的代码应尽可能相邻。

## 10. 表达式

### 规则

- **规则 10.1**：表达式的值在标准所允许的任何运算次序下都应该是相同的。注意自增/自减操作符、函数参数计算次序、函数指针与参数、嵌套赋值语句、`volatile` 访问等问题。

### 建议

- **建议 10.1**：函数调用不要作为另一个函数的参数使用。
- **建议 10.2**：赋值语句不要写在 `if` 等语句中，或者作为函数的参数使用。
- **建议 10.3**：用括号明确表达式的操作顺序，避免过分依赖默认优先级。
- **建议 10.4**：赋值操作符不能使用在产生布尔值的表达式上（避免 `=` 与 `==` 混淆）。

---

## 11. 代码编辑、编译

### 规则

- **规则 11.1**：使用编译器的最高告警级别，理解所有告警，通过**修改代码**而不是降低告警级别来消除所有告警。
- **规则 11.2**：在产品软件中，统一编译开关、静态检查选项以及相应告警清除策略。
- **规则 11.3**：本地构建工具的配置应该和持续集成的一致。

---

## 12. 可测性 & 单元测试

- 代码设计应具备可测试性（发现故障、隔离定位故障的能力）。
- 单元测试应覆盖所有对外接口函数。
- 单元测试应覆盖正常情况、边界情况和异常情况。
- 建议使用 TDD（测试驱动开发）方法。

---

## 13. 安全性（基础）

这是从 C 语言编程规范中提取的安全基础要求，更全面的安全规范参见 `c-secure-coding-standard` 技能。

### 规则

- **规则 13.1**：字符串操作安全 — 使用 `snprintf`/`strncpy`/`strncat`/`fgets` 替代 `sprintf`/`strcpy`/`strcat`/`gets`。
- **规则 13.2**：整数安全 — 整数运算时严格检查，确保不会出现溢出、反转、除 0。
- **规则 13.3**：格式化输出安全 — 禁止 format 参数由外部可控。
- **规则 13.4**：文件 I/O 安全 — 创建文件时必须显式指定合适的访问权限；对文件路径进行规范化后再使用。

---

## 14. 可移植性

- 避免使用特定平台的 API 和扩展。
- 注意不同平台的数据类型大小差异（使用 `sizeof` 而非假设）。
- 通讯结构注意字节序（大小端问题）。
- 使用标准 C 库函数，避免使用 POSIX 特有函数。

## 检查清单

审查 C 语言代码时，按以下清单逐项检查：

1. ☐ 头文件是否职责单一、自包含、有保护符？
2. ☐ 函数是否短小（≤50 行）、嵌套浅（≤4 层）、职责单一？
3. ☐ 命名是否清晰、统一（不使用匈牙利命名法）？
4. ☐ 全局/静态变量是否加了 `g_`/`s_` 前缀？
5. ☐ 变量是否声明即初始化、一个变量只有一个功能？
6. ☐ 宏是否用了完备括号、多条语句用 `do-while(0)` 包裹？
7. ☐ 是否避免了魔鬼数字？
8. ☐ 是否存在内存越界、内存泄漏、引用已释放内存？
9. ☐ `if-else if` 是否有 `else` 结尾？`switch` 是否有 `default`？
10. ☐ 错误返回码是否全面处理？
11. ☐ 注释是否说明"为什么"而非"做什么"？
12. ☐ 格式是否统一（4 空格缩进、一行一条语句）？
13. ☐ 表达式是否在任何运算次序下都相同？
14. ☐ 是否使用了编译器最高告警级别？
15. ☐ 是否使用了安全函数替代危险字符串函数？
